# 版本控制

本项目在 2026-10-30 补建 Git。`main` 是正常开发与发布分支。

## 历史的可信范围

`history:` 开头的提交从服务器已有发布备份逐份恢复，涵盖 v1.7.4 至 v2.2.0 的主要功能发布和保存下来的检查点。它们不是当时的原始 Git 提交，提交时间是恢复时间，作者使用项目维护身份；没有伪造过去的提交时间或个人作者。

历史备份有的只包含变更文件，因此 `recovered/v*` 标签供审阅、追溯与差异参考，不保证每个早期提交都是可独立部署的完整源码。无法恢复没有留下备份的中间编辑。来源、原始压缩包 SHA-256 和对应提交见 `recovered-history.json`。

`v2.2.0` 标签是初始化时与线上核对的完整源码基线。从此之后，正常修改按任务逐次提交；Git 不会自动记录尚未保存或尚未提交的编辑。

## 每次修改的流程

1. `git status`；确认没有其他人的未提交工作，再 `git pull --ff-only`。
2. 完成一个独立修改，检查差异，运行适用的测试。
3. 只暂存这次任务的源码文件，然后 `git commit -m "fix: 描述具体修改"`（功能用 `feat:`、维护用 `chore:`）。
4. `git push origin main`。本机修改后在服务器快进拉取；服务器直接修改后，本机再快进拉取。部署与重启仍按原流程执行，推送本身不会自动重启应用。
5. 对正式发布添加版本标签，再显式推送对应标签。

查看历史：`git log --oneline --decorate`；查看单次改动：`git show <提交>`；对比版本：`git diff <旧版本>..<新版本>`。需要撤销已发布修改时，优先使用 `git revert`，不要强制回退主分支。

## 密钥与数据排除

`.gitignore` 排除密钥、运行数据、图片上传、日志和发布包；仅跟踪无真实凭据的 `.env.example`。提交钩子还会检查暂存文件名与常见密钥格式；这不代替人工检查差异。

新克隆需执行 `git config core.hooksPath .githooks`。本次创建的服务器工作目录和本机克隆已配置。钩子只做检查，不会自动暂存、提交或发送代码。

提交作者使用 `Math Notes Maintenance <maintenance@math-notes.invalid>`，仅作用于本项目。可按实际维护者身份修改仓库级 Git 配置。
